# Правила разработки C++17

Статус: обязательные требования к новому коду проекта. Отступления объясняются в review конкретной необходимостью и проверкой. Правила применяются к собственному коду, не требуют переписывать зависимости.

## Типы и интерфейсы

- Стандарт C++17 без compiler extensions. C++20/23 std::span, std::jthread и std::expected не используются как будто они доступны в C++17.
- Domain содержит небольшие типы значений, enum class, explicit-конструкторы и проверяемые инварианты. Идентификаторы, радианы, метры и длительности различаются типами там, где смешение опасно. Для длительностей используется std::chrono.
- Суставные данные приводятся к порядку проверенной модели на границе адаптера. Голый vector<double> без связи с моделью и набором суставов не является публичной целью.
- std::optional означает отсутствие значения, std::variant подходит для взаимоисключающих целей и результата value/error. Выбор единого Result<T> фиксируется при первом использовании; собственный универсальный framework ошибок не создается.
- Ожидаемые отказы возвращаются типизированным результатом с [[nodiscard]]. Неверная цель, отсутствие пути и занятый робот не являются исключительными ситуациями.
- Исключения зависимостей перехватываются на границе адаптера/callback и переводятся в результат или отказ запуска. Запрещено проглатывать исключение и сообщать успех. assert проверяет внутренние инварианты, но не заменяет валидацию внешнего ввода.
- Интерфейсы портов имеют виртуальный деструктор, если используются полиморфно. Предпочтительны композиция, функции и конкретные типы; наследование служит заменяемым адаптерам.

## Владение и ресурсы

- RAII для памяти, файлов, потоков, блокировок и соединений. По умолчанию владение значением или unique_ptr; shared_ptr только при реальном совместном владении, в том числе требованиях ROS API.
- Сырые указатели и ссылки не владеют объектом. Время жизни string_view и ссылок явно ограничено; асинхронная операция владеет нужными ей данными.
- Правило нуля предпочтительно. Копирование владельцев потока/соединения запрещено; move и noexcept задаются по фактическим гарантиям.
- Нет detached threads, mutable globals и singleton состояния робота. Composition root создает зависимости и управляет порядком завершения.
- Callback не захватывает сырой this, если может пережить объект. Shutdown сначала прекращает прием команд, затем отменяет/сверяет операции, завершает workers и только затем разрушает адаптеры.
- Внешний вызов или пользовательский callback не выполняется под mutex. Данные защищаются одним ясно указанным механизмом; volatile не используется для синхронизации.

Эти правила владения, RAII и интерфейсов опираются на [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines). Выбор Result и политика ожидаемых отказов выше являются решениями проекта.

## Организация кода и сборки

- Отдельные CMake targets для Domain, Application и адаптеров; зависимости задаются через target_link_libraries с корректными PUBLIC/PRIVATE. Глобальные include_directories и флаги не распространяют зависимости между слоями.
- Публичные заголовки самодостаточны и включают только необходимое. Нет using namespace в заголовках и каталогов common/utils для несвязанных функций.
- Namespace отражает модуль: manipulator::domain, manipulator::application, manipulator::adapters. Типы именуются PascalCase, функции и переменные snake_case, файлы snake_case.hpp/.cpp. API ROS сохраняет требуемые внешним framework имена.
- Комментарий объясняет инвариант, единицы, владение или причину решения. Контракты портов документируют потоки вызова, время жизни, ошибки и отмену.
- clang-format и ограниченный профиль clang-tidy фиксируются в репозитории вместе с версиями инструментов. Предупреждения собственного кода (-Wall, -Wextra, -Wpedantic) считаются ошибками в CI; сторонние заголовки не редактируются ради подавления их предупреждений.
- Конфигурация робота валидируется целиком до ready. Неизвестные критичные параметры и несовместимые версии дают отказ запуска, а не тихие defaults.

## Проверяемые требования

1. Core собирается и тестируется без ROS, HTTP и SDK оборудования, с GCC и Clang в C++17.
2. Тесты сценариев используют fake-порты и управляемые часы, а не sleep для ожидания состояния.
3. Модульные проверки инвариантов и автомата дополняются контрактными тестами адаптеров и интеграцией с ros2_control mock.
4. ASan/UBSan запускаются для собственного кода в отдельной конфигурации; TSan применяется отдельным запуском к конкурентным компонентам. Ограничения инструмента для внешних библиотек документируются.
5. Review проверяет владение, направление зависимостей, гонки, повторы команд, тайм-ауты и ошибки. Процент покрытия сам по себе не является критерием качества.
6. Для аппаратного цикла отдельно измеряются задержки и расход памяти; тесты в обычном Linux и статический анализ не доказывают real-time свойства.

До появления исходников это требования, а не настроенные проверки. Конфигурации CMake, форматирования и CI добавляются на этапе каркаса и становятся обязательными при первом merge кода.
