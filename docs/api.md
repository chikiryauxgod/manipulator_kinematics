# Контракт прикладного API v1

Статус: проектный контракт; endpoints пока не реализованы. До реализации шлюза создать OpenAPI для HTTP и JSON Schema для событий и примеров. Изменения контрактов проходят вместе с контрактными тестами.

## Уровни API

1. Публичный HTTP/WebSocket API: версионируемые DTO для клиента, без ROS-типов.
2. Входной API Application: типизированные команды и результаты, без сериализации.
3. Выходные порты Application: планирование, исполнение, состояние и время.
4. ROS и аппаратные протоколы: адаптеры переводят внешние данные и ошибки.

Веб-шлюз валидирует структуру и размер запроса. Application проверяет право управления и предметные инварианты независимо от шлюза, включая команды других ROS-клиентов. Контроллер проверяет свои ограничения при исполнении.

## Ресурсы HTTP

Префикс: `/api/v1`. Для первого запуска используется один robot_id, явно присутствующий в маршрутах.

| Метод и путь относительно префикса | Семантика |
| --- | --- |
| GET /robots/{robot_id} | Описание, версии модели и калибровки, суставы, пределы, системы координат и capabilities |
| GET /robots/{robot_id}/state | Согласованный снимок, readiness, active_operation_id, свежесть данных и epoch |
| POST /robots/{robot_id}/control-leases | Получить исключительное право управления; 409, если занято |
| POST /robots/{robot_id}/control-leases/{lease_id}/renew | Продлить право управления при действительном токене |
| DELETE /robots/{robot_id}/control-leases/{lease_id} | Отозвать право, запросить отмену активной операции |
| POST /robots/{robot_id}/plans | Принять расчет цели, вернуть 202 и operation_id |
| GET /robots/{robot_id}/plans/{plan_id} | Получить неизменяемый план для предпросмотра и срок действия |
| POST /robots/{robot_id}/executions | Принять plan_id на выполнение, вернуть 202 и operation_id |
| GET /robots/{robot_id}/operations/{operation_id} | Текущее состояние и результат операции |
| POST /robots/{robot_id}/operations/{operation_id}/cancel | Идемпотентно запросить отмену; 202 до подтверждения исполнителем |

Ответ 202 означает принятие операции, а не успешное планирование или движение. Успех расчета содержит plan_id. Завершенная операция хранится в пределах опубликованного retention; неизвестный ID возвращает 404, известный удаленный ресурс 410, пока сохранен tombstone.

Пример тела расчета суставной цели (имена здесь условные, фактические берутся из описания):

```json
{
  "target": {
    "type": "joint",
    "positions_rad": {"joint_1": 0.0, "joint_2": -1.0, "joint_3": 1.0,
                      "joint_4": 0.0, "joint_5": 0.5, "joint_6": 0.0}
  },
  "velocity_scale": 0.2,
  "acceleration_scale": 0.2
}
```

Суставная цель содержит ровно все суставы группы, без неизвестных или повторных имен. Декартова цель имеет type=pose, frame_id, tool_frame_id, position_m с x/y/z и orientation_xyzw из четырех чисел. Степени и Euler-углы допускаются только как представление UI. Масштабы находятся в (0, 1]; они применяются к серверным ограничениям, а не заменяют их. Все числа конечны, размер тела и число точек ответа ограничены конфигурацией.

## Идентификаторы, повторы и полномочия

- robot_id, operation_id, plan_id и lease_id непрозрачны и не взаимозаменяемы. server_epoch меняется при каждом запуске сервиса управления.
- Все изменяющие POST-запросы требуют Idempotency-Key. Application сериализует дедупликацию и принятие команды: один ключ в области robot_id, server_epoch и управляющего сеанса с тем же каноническим телом возвращает ту же операцию; другое тело дает 409 idempotency_conflict.
- Для выдачи lease область дедупликации привязана к проверенному клиентскому сеансу. Токены не передаются в URL и не журналируются. Право управления проверяется сервером; знание lease_id не является полномочием.
- Срок хранения ключа публикуется вместе с возможностями API и не меньше срока операции плюс окна повторов. В пределах epoch истекшие использованные ключи отклоняются; клиент не повторяет команды после истечения окна или смены epoch.
- В первой версии дедупликация хранится в памяти. После рестарта старые изменяющие запросы с прежним epoch отклоняются; планы и leases недействительны. Новое движение запрещено до сверки с исполнителем. Гарантия exactly-once при сбоях сети не заявляется.
- Lease имеет монотонный срок действия на сервере. HTTP-запрос или открытый WebSocket не продлевают его автоматически. Истечение блокирует новые команды и инициирует отмену; новое право движения не выдается до разрешения неопределенного исполнения.
- Локальная демонстрация слушает loopback. Для доступа по сети перед включением требуются аутентификация клиента, защищенный транспорт, проверка Origin и разграничение чтения/управления. Lease не заменяет аутентификацию.

## Операции и готовность

Планирование: accepted -> planning -> succeeded | failed | canceled. Успех создает отдельный ресурс плана.

Исполнение: accepted -> executing -> succeeded | failed. Отмена: accepted/executing -> cancel_requested -> canceled после подтверждения; если завершение опередило отмену, результат succeeded или failed сохраняется. Терминальный результат не переписывается поздним callback.

При потере достоверного статуса исполнение переходит в execution_unknown. Это нетерминальное состояние требует сверки: можно восстановить executing либо подтвержденный терминальный результат. Тайм-аут ожидания клиентом не переводит движение в failed и не освобождает слот исполнения. Во время cancel_requested новые задания не исполняются.

Readiness робота отдельно принимает initializing, ready, not_ready, fault или execution_unknown. Готовность основывается на свежести состояния, контроллере, калибровке и аппаратных разрешениях. Успех mock-исполнения подтверждается результатом контроллера и конечной позой в допуске; для оборудования добавляются проверки остановки и состояния приводов.

## Ошибки

Ошибка содержит стабильный code, message для человека, request_id, необязательные operation_id и структурированные details. Клиент принимает решения по code. Stack trace, токены и внутренние пути в публичный ответ не включаются.

| HTTP | Примеры кода при отказе принять запрос |
| --- | --- |
| 400 | malformed_request |
| 401 / 403 | unauthenticated / control_denied |
| 404 / 410 | resource_not_found / resource_expired |
| 409 | robot_busy, stale_plan, idempotency_conflict, epoch_mismatch |
| 422 | invalid_target, invalid_frame, capability_not_supported |
| 429 | queue_full |
| 503 | controller_unavailable, state_stale |

Если операция уже принята, no_path, planning_timeout или execution_fault возвращаются в ее результате, а GET операции остается успешным HTTP-ответом. Неопределенность исполнения передается состоянием, а не советом автоматически повторить команду.

## События и восстановление

WebSocket `/api/v1/events?robot_id=...` передает snapshot, robot_state, operation_updated и resync_required. Конверт содержит schema_version, server_epoch, seq, robot_id, type, occurred_at и payload. seq упорядочивает сообщения внутри epoch; occurred_at не используется как дедлайн.

При подключении сервер атомарно формирует снимок с seq и регистрирует последующие обновления, чтобы между ними не потерялся результат. Для первой версии возобновление старого потока не гарантируется: при разрыве, пропуске seq или смене epoch клиент запрашивает новый snapshot. Скорость телеметрии ограничена, частые состояния можно объединять. Медленный клиент получает resync_required либо закрытие соединения; очереди не растут бесконечно.

HTTP GET остается способом сверки после потери события. Жизненный цикл задания хранит Application, а не WebSocket-соединение или браузер.

## Совместимость и приемка

Новые необязательные поля могут добавляться внутри v1; удаление полей, изменение единиц или значения существующих полей требует новой major-версии. Неизвестный статус UI показывает как неподдерживаемый и блокирует команды, не трактуя его как ready. ROS DTO версионируются отдельно и преобразуются адаптером.

Контрактные тесты проверяют схемы запросов и ответов, повтор ключа, гонку двух executions, отмену при завершении, истечение lease, reconnect между snapshot и событием, смену epoch и потерю ответа контроллера. До этих проверок API не считается готовым к браузерному сценарию.
